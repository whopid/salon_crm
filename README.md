# Salon CRM

----------------------
Backend API CRM-системы для управления работой салона красоты. Проект предназначен для хранения информации о клиентах, мастерах и услугах, а также для создания и управления записями на процедуры.



**Основной акцент проекта** — корректная работа с расписанием мастеров и предотвращение конфликтующих бронирований на уровне базы данных.

----------------------

### Возможности

* Управление клиентами салона.

* Управление мастерами.

* Управление услугами и их стоимостью.

* Создание записей с автоматическим расчётом времени окончания процедуры.

* Проверка существования клиента, мастера и услуги при создании записи.

* Защита от пересечения активных записей одного мастера.

* Миграции схемы базы данных с помощью Alembic.

* Автоматизированные тесты API.
----------------------
### Технологический стек

***Python*** — основной язык разработки.

***FastAPI*** — создание REST API.

***SQLModel*** — модели данных и взаимодействие с базой данных.

***PostgreSQL*** — реляционная база данных.

### Запуск проекта

**Требования**

* Python 3.13+.

* Docker и Docker Compose.


**Клонирование репозитория**
```
git clone git@github.com:whopid/salon_crm.git
cd salon_crm
```

**Настройка переменных окружения**

Создайте файл .env в корне проекта и укажите параметры подключения к PostgreSQL. Названия переменных должны соответствовать используемым в проекте настройкам.

**Запуск PostgreSQL**
```
docker compose up -d
```


**Установка зависимостей**

Активируйте виртуальное окружение и установите зависимости проекта.
```
pip install -r requirements.txt
```


**Применение миграций**

Из корня проекта выполните:
```
alembic upgrade head
```


**Запуск API**
```
uvicorn app.main:app
```


Документация Swagger UI: http://127.0.0.1:8000/docs

### Примеры запросов

**Получение списка услуг**
```
curl http://127.0.0.1:8000/services
```

**Создание записи**
```
curl -X POST http://127.0.0.1:8000/appointments \
  -H "Content-Type: application/json" \
  -d '{
    "client_id": "UUID_КЛИЕНТА",
    "master_id": "UUID_МАСТЕРА",
    "service_id": "UUID_УСЛУГИ",
    "starts_at": "2026-11-10T10:00:00+00:00"
  }'
```

При успешном создании API возвращает 201 Created и данные записи, включая рассчитанное время окончания процедуры.

**Обработка конфликтующего бронирования**

Если у выбранного мастера уже есть активная запись на пересекающийся интервал:
```
curl -X POST http://127.0.0.1:8000/appointments \
  -H "Content-Type: application/json" \
  -d '{
    "client_id": "UUID_КЛИЕНТА",
    "master_id": "UUID_МАСТЕРА",
    "service_id": "UUID_УСЛУГИ",
    "starts_at": "2026-11-10T10:30:00+00:00"
  }'
```

При конфликте API возвращает 409 Conflict.

### Проблемы и решения

#### Предотвращение пересечения записей

**Проблема**: 
> Один мастер не должен иметь две активные записи на пересекающееся время. Проверка только на уровне API не гарантирует целостность данных при конкурентных запросах: несколько запросов могут одновременно проверить доступность интервала и попытаться создать записи.

**Решение**: 
> Для защиты от пересечений используется ограничение PostgreSQL EXCLUDE с индексом GiST и функцией tstzrange.
```
EXCLUDE USING gist (
    master_id WITH =,
    tstzrange(starts_at, ends_at, '[)') WITH &&
)
WHERE (status IN ('scheduled', 'confirmed'))
```

Ограничение запрещает сохранять записи одного мастера, если их временные интервалы пересекаются и обе записи имеют статус scheduled или confirmed.

Используется полуоткрытый интервал [): время начала включается в диапазон, а время окончания — нет. Поэтому последовательные записи, например с 10:00 до 11:00 и с 11:00 до 12:00, допустимы. Отменённые и завершённые записи не блокируют последующие бронирования.

Такой подход переносит обеспечение целостности данных на уровень базы данных и защищает от конфликтов даже при конкурентном выполнении запросов.

#### Обработка ошибок при сохранении записи

**Проблема**: 
> При попытке создать запись, нарушающую ограничение базы данных, API должен корректно обработать ошибку и вернуть клиенту понятный HTTP-ответ.

**Решение**: 
> Создание записи выполняется в транзакции. При успешном сохранении изменения фиксируются через commit(). Если возникает IntegrityError, выполняется rollback(), а клиент получает ответ 409 Conflict.

Предварительные проверки в API используются для обработки ожидаемых ситуаций, например отсутствия клиента, мастера или услуги (404 Not Found). Однако окончательная защита от пересечения записей обеспечивается ограничением PostgreSQL, а не только проверками в приложении.



#### Автоматический расчёт времени окончания

**Проблема**: 
> Передача времени окончания и длительности процедуры от клиента может привести к несогласованным данным, например если указанная длительность не соответствует выбранной услуге.

**Решение**: 
> Значение ends_at рассчитывается на сервере на основе времени начала записи и длительности выбранной услуги, сохранённой в базе данных:
```
ends_at = starts_at + timedelta(
    minutes=service.duration_minutes
)
```

Это исключает необходимость передавать длительность процедуры в запросе и позволяет использовать единый источник данных о продолжительности услуги.

#### Управление изменениями схемы базы данных

**Проблема**: 
> При изменении моделей необходимо синхронизировать структуру базы данных с кодом приложения и обеспечить воспроизводимое развёртывание проекта в разных окружениях.

**Решение**: 
> Для управления схемой базы данных используется Alembic. Миграции фиксируют изменения структуры БД и позволяют последовательно применять их без ручного создания и изменения таблиц.

### Структура базы данных



**Основные сущности проекта:**



**_User_** — учётные записи пользователей системы и роли доступа.

**_Client_** — клиенты салона.

**_Master_** — мастера, выполняющие процедуры.

**_Service_** — услуги, их стоимость и длительность.

**_Appointment_** — записи клиентов к мастерам на услуги.



Связи между сущностями реализованы с помощью внешних ключей. Запись содержит ссылки на клиента, мастера и услугу.

### Тестирование

Для запуска тестов выполните:
```
python -m pytest -v
```


Тесты должны использовать отдельную тестовую базу данных, чтобы не изменять данные основной базы. Перед запуском тестов необходимо настроить TEST_DATABASE_URL и применить миграции к тестовой базе.



**Основные сценарии тестирования:**



* Успешное создание записи и корректный расчёт ends_at.

* Отклонение повторной записи на тот же интервал.

* Отклонение частично пересекающихся записей одного мастера.

* Успешное создание записи после отмены другой записи, использующей то же время.

* Корректная обработка ошибок целостности базы данных.

**Какие тесты наиболее важны**

Наиболее важны тесты, проверяющие не только успешное создание записи, но и соблюдение бизнес-правил:

* создание записи возвращает 201 Created, а ends_at рассчитывается правильно;

* повторная запись на тот же интервал отклоняется;

* частичное пересечение интервалов одного мастера отклоняется;

* после отмены записи её интервал можно использовать повторно;

* некорректные ссылки на клиента, мастера или услугу обрабатываются ожидаемым образом.

Эти сценарии проверяют ключевые требования к расписанию и помогают убедиться, что ограничения работают на практике.
